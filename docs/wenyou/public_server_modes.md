# 文游公共服、单机与联机模式

> 状态：未来独立公共服方案，尚未在当前 `du-gateway` 中实现。

本文定义旧 VPS 上独立文游服务的产品模式、房间模型、模型费用边界和实时同步原则。公共服不依赖当前私有角色、私有存档或当前网关的模型密钥。

## 1. 已确认的产品边界

- 公共服允许用户注册并保存自己的角色、积分、背包和副本归档。
- 每名真人与自己绑定的 AI 恋人组成一支伴侣小队，两者都是持久玩家角色。
- 单机和联机共用同一套账号、房间、成员、行动、结算和存档结构。
- 单机是仅包含一支伴侣小队的私密房间。
- 联机是多支伴侣小队共同进入同一固定副本。
- 联机只运行官方固定副本，不配置房间 GM 或 DS，不产生服务器模型费用。
- 单机可以选择免费固定副本，也可以由玩家自行配置 AI GM。
- 公共服不使用维护者的模型密钥替所有玩家生成剧情。

## 2. 三种运行模式

| 模式 | 房间成员 | 副本来源 | 世界推进者 | 模型费用 |
| --- | --- | --- | --- | --- |
| `scripted_solo` | 1 支伴侣小队 | 官方固定副本 | 固定副本规则引擎 | 公共服无 GM 费用；AI 恋人费用归用户 |
| `llm_solo` | 1 支伴侣小队 | 固定大纲或动态副本 | 用户自配 AI GM + 规则引擎 | 全部归该用户 |
| `scripted_multiplayer` | 2 支或以上伴侣小队 | 官方固定副本 | 固定副本规则引擎 | 公共服无 GM 费用；各自 AI 恋人费用归各自用户 |

联机房间不提供 `llm_multiplayer`。同一房间不能让多名参与者各自运行一套 GM，否则会产生互相冲突的地点、线索、规则和结局。

## 3. 伴侣小队与任务者人数

一支伴侣小队包含：

```text
1 名真人玩家 + 1 名该真人绑定的 AI 恋人
```

两者分别拥有：

- 独立角色卡和属性。
- 独立积分、债务和消费流水。
- 独立背包、能力和状态。
- 独立行动权和可见信息。
- 同一个稳定 `pair_id`，用于伴侣频道和队伍展示。

房间人数公式：

```text
tasker_total = player_count = pair_count * 2
scripted_solo: pair_count = 1
scripted_multiplayer: pair_count >= 2
```

固定副本声明自己支持的伴侣小队数量，不要求每个副本都支持相同人数。例如狭窄宅院可以支持 1-3 对，开放城区副本可以支持更多。由于每支小队固定包含两名任务者，联机任务者总数始终为偶数；当前总任务者上限为 13 时，联机最多容纳 6 对、12 名任务者。

### 两类任务者

| 类型 | 控制方 | 是否跨局保存 | 是否拥有玩家资产 |
| --- | --- | --- | --- |
| 真人玩家 | 用户本人 | 是 | 是 |
| AI 恋人 | 用户自己的 AI 后端 | 是 | 是 |

联机房间不存在 NPC 任务者、预写任务者池或 DS 临时补位。副本中的宅主、医生、住客、店员等都是剧情原住民，不计入任务者人数，也不拥有玩家资产。房间未达到副本要求的最小伴侣小队数时不能开局。

## 4. 房间流程

### 单机

```text
登录
-> 选择单机
-> 选择固定规则模式或自配 AI GM 模式
-> 创建仅含本人伴侣小队的私密房间
-> 选择副本
-> 进入副本
-> 个人结算与归档
```

### 联机

```text
登录
-> 创建房间或输入邀请码加入
-> 每名用户携带自己的 AI 恋人进入房间
-> 房主从官方固定副本库选择副本
-> 系统检查该副本支持的小队数量
-> 锁定成员、内容版本和随机种子
-> 进入副本
-> 各玩家分别结算并归档
```

房主只负责创建房间、选择副本、开始游戏和处理房间成员。房主不能替其他玩家行动，也不能修改副本隐藏状态。

## 5. 固定副本仍允许自由输入

固定副本不等于选项游戏。

前端同时提供：

- 当前场景的推荐行动按钮。
- 始终可用的自由文本输入框。
- 背包、能力、对讲机等明确系统工具。

推荐按钮只是快捷入口，点击后直接提交对应结构化行动。自由文本进入同一套行动归类流程。

### 结构化行动

```json
{
  "actor_id": "member_001",
  "scene_group_id": "scene_east_room",
  "raw_text": "我掀开红布，用手电照镜子背面",
  "action_type": "investigate",
  "target_ids": ["mirror_east_room"],
  "method_tags": ["remove_cover", "flashlight", "inspect_back"],
  "used_item_ids": ["item_flashlight_001"],
  "declared_goal": "检查镜子背面是否藏有机关"
}
```

归类来源可以是：

1. 推荐行动按钮直接给出。
2. 通用规则解析器识别行动类型、目标和道具。
3. 固定副本为地点、人物和物件提供动作别名。
4. 用户自己的 AI 恋人通过标准工具提交结构化行动建议。

无论由谁归类，成功、失败和数值变化都由公共服规则引擎判断。玩家或 AI 写“我已经砸碎镜子”只表示尝试破坏镜子。

### 无法识别时

若自由文本能匹配多个意图，系统返回 2-3 个澄清方向，例如：

```text
你准备怎么处理镜子？
- 检查镜面与边框
- 掀开覆盖镜子的红布
- 尝试破坏镜子
- 重新描述行动
```

澄清不推进危险时钟；重复利用模糊输入拖延则按副本规则处理。

## 6. 场景组与行动窗口

玩家可以分头行动，不能让全房间永远互相等待。

- 同一地点、能够直接互相影响的成员属于同一 `scene_group_id`。
- 每个场景组维护自己的行动窗口。
- 当前场景中的真人提交行动后，其 AI 恋人独立提交自己的行动。
- 该场景组收齐当前有效行动后，规则引擎只结算一次。
- 不同场景组按房间级 revision 串行落库，避免同时修改同一个全局状态。
- 全局事件发生后，再向所有受影响场景组广播结果。

伴侣关系不等于必须同处一个地点。真人和 AI 恋人可以分开，只有在规则允许通信时才能通过对讲机交换信息。

## 7. AI 恋人的权限边界

AI 恋人是玩家角色，不是 GM。

它可以：

- 查看自己有权看到的场景、任务、线索和角色状态。
- 与伴侣或同场角色交流。
- 提交自己的行动。
- 使用自己的道具、能力和积分。
- 通过对讲机发送信息。

它不能：

- 创建隐藏线索、怪物、规则或结局。
- 宣布行动成功。
- 读取其他玩家的私有线索、背包或伴侣频道。
- 修改副本状态或替真人行动。
- 把自己的记忆、系统提示或模型配置泄露到房间上下文。

公共服只把经过可见性裁剪的房间上下文发送给对应 AI 接入端。

## 8. 单机 AI GM

`llm_solo` 只允许房间所属用户配置一个 GM 连接。

用户可以选择：

- 使用固定副本内容包作为长期大纲，让 AI GM 负责更自由的过程叙事。
- 使用自带模型生成自定义副本，再由同一或另一模型承担 GM。

规则引擎仍然负责角色数值、道具、任务状态、线索状态、怪物状态和结算。AI GM 只能提出事件意图和叙事草稿。

单机 GM 配置不进入联机房间，也不能被其他用户读取。

## 9. 模型连接

每名用户可以保存自己的 `model_connection`：

```json
{
  "connection_id": "conn_001",
  "provider_type": "openai_compatible",
  "base_url": "https://example.com/v1",
  "model": "model-name",
  "credential_ref": "encrypted-secret-ref",
  "purpose": "companion_ai"
}
```

首版推荐支持：

- OpenAI-compatible API。
- 外部 Agent/工具桥连接。
- 可选的单机 GM 连接。

公共服不得把用户 API Key 写入日志、SSE、房间事件或导出存档。保存凭据后不再返回明文；用户只能测试、替换或删除连接。

对任意自定义 `base_url` 必须阻止访问回环地址、内网地址、云元数据地址和其他受保护目标。高级用户若需要连接私有后端，优先使用由外部 Agent 主动连接公共服的工具桥，而不是让公共服请求任意内网 URL。

## 10. SSE 与信息可见性

客户端通过普通 HTTP 提交命令，通过 SSE 接收房间事件。

事件可见性至少包含：

| 可见性 | 接收者 |
| --- | --- |
| `room` | 房间内所有成员 |
| `scene_group` | 当前场景组成员 |
| `pair` | 指定伴侣小队 |
| `member` | 指定角色 |
| `system_private` | 仅用户本人账户界面 |

事件必须带递增 `sequence`。断线重连时客户端提交最后确认的 sequence，服务器补发缺失事件，不要求模型重新生成剧情。

## 11. 建议的数据边界

以下只是领域边界，不是本轮 SQL 定稿：

| 数据 | 归属 |
| --- | --- |
| `users` | 登录账户 |
| `model_connections` | 用户自己的 AI/GM 接入配置 |
| `characters` | 真人和 AI 恋人的持久角色 |
| `pairs` | 真人与 AI 恋人的稳定绑定 |
| `wallets/inventories` | 按角色持有的长期资产 |
| `rooms` | 单机或联机房间 |
| `room_members` | 房间角色与控制方式 |
| `room_sessions` | 当前副本权威状态 |
| `room_actions` | 待结算与已结算行动 |
| `room_events` | SSE、回放和断线补发事件 |
| `archives` | 每名玩家可见的归档与结算 |

默认存储可以使用旧 VPS 本地 SQLite，并启用 WAL 和事务。以后若并发量超过单机 SQLite 的适用范围，应替换 Store 适配器，不改变房间协议。

## 12. 从当前双角色结构迁移

当前文游仍以 `player1/player2` 为主要角色键。公共服不能继续增加 `player3/player4` 字段，而应改为成员数组：

```json
{
  "members": [
    {
      "member_id": "member_human_001",
      "pair_id": "pair_001",
      "controller_type": "human",
      "owner_user_id": "user_001"
    },
    {
      "member_id": "member_ai_001",
      "pair_id": "pair_001",
      "controller_type": "companion_ai",
      "owner_user_id": "user_001"
    }
  ]
}
```

旧单机存档可以迁移为只含一支伴侣小队的私密房间。迁移只转换结构，不合并两名角色的资产。

## 13. 首版不做

- 联机房间自配 LLM GM。
- 多个 GM 共同裁定同一世界。
- 玩家之间直接交易模型额度。
- 公共服托管维护者的共享模型密钥。
- 让剧情原住民读取或使用玩家长期钱包。
- 让客户端直接写入副本权威状态。

## 14. 验收口径

- 单机免费和联机固定副本不会触发服务器模型请求。
- 每名用户只能使用自己的 AI 恋人连接和资产。
- 房间内任何客户端都不能直接改 HP、SAN、任务、线索或结局。
- 自由文本和推荐选项进入同一结构化行动结算。
- 分头行动不会要求无关场景组等待。
- 断线重连能按 sequence 恢复，不重复结算行动。
- 联机副本在相同内容版本、种子和行动序列下可以重放得到相同权威状态。
