# 渡参与的新游戏接入规范

这份规范是 `du-gateway` 新增或修改游戏接入时的强制合同。它解决的不是“页面能打开”或“工具能调用”，而是渡是否从入口到后续上下文都以正确身份参与了游戏。

任何一项缺失，都不能写“游戏已接入”“渡能玩”或“互动链已完成”。

## 1. 先分类，不得混接

每条模型参与链必须先二选一：

1. **A 类：渡自主单机游戏**
   - 渡自己决定要玩，并通过游戏工具实际推进。
   - 现行参考：植物大战丧尸随机版、AI 农场、瓶中生态的主动游戏执行轮。
   - 它不是小玥正在与渡进行的一轮真实互动，不得刷新共同游戏互动时间。

2. **B 类：小玥与渡真实互动游戏**
   - 小玥在 App 内与渡共享同一局状态，双方动作互相影响。
   - 现行参考：涩涩走格棋、五子棋、囚禁模拟器的共同游戏唤醒链。
   - 必须保留主聊天近期摘要和 `last4`，并把真实参与写入统一互动时间。

一个产品可以同时具备 A、B 两类参与方式，但必须建立两个独立 adapter，分别填写清单、注册入口和验收。不得因为已有 App 页面就默认模型已参与，也不得因为渡能调用工具就默认这是双人互动游戏。

## 2. 每个游戏先填写唯一接入清单

施工前必须在设计或 Task Ticket 中逐项写明以下字段；不得用“相关入口”“按现有方式”代替具体值。

| 字段 | 必填内容 |
| --- | --- |
| 参与类型 | A 类、B 类；两类兼有时写两行 |
| `game_id` | 唯一、稳定、全链一致的 ASCII ID |
| 中文名与别名 | 展示名、路由别名、模型选择别名 |
| 权威状态 | 引擎、存档路径、当前局 ID、原子写入方式 |
| App 入口 | 游戏大厅卡片、目标页面、加载/重试/结束入口 |
| 网关入口 | 状态 API、动作 API、模型同步 API 或工具执行器 |
| 模型入口 | 单机执行轮或共同游戏 wakeup wrapper |
| 模型可用能力 | 唯一工具、精确首行协议，或两者都无 |
| 专用请求身份 | `wakeup_kind`、对应 header、生产端、所有消费者 |
| system/user 合同 | system 来源、动态槽位、user 来源、空 user 文案 |
| 动作落地 | 解析器、允许动作矩阵、状态机权威写入点 |
| 局内存档 | 棋局状态、局内聊天、结束/重开清理规则 |
| 主聊天归档 | 事件源、专用标签、压缩文案、assistant 保存规则 |
| 后续上下文 | 近期摘要、`last4`、工具结果摘要如何识别本游戏 |
| 活动记录 | 单机执行记录或共同游戏互动时间事件矩阵 |
| 验证 | 旧实现失败证据、定向回归、最终请求与下一轮上下文 |
| 发布 | 网关文件、原生文件、实际加载服务及独立验收边界 |

## 3. 全局不变量

### 3.1 稳定 ID 必须贯穿全链

同一个 `game_id` 必须贯穿注册表、别名、保存目录、路由、工具、header 或 `wakeup_kind`、归档识别、活动记录、客户端 DTO、测试和日志。不同层不得各造一套近似名称。

需要兼容旧名称时，别名只在统一 normalize 层收敛到唯一 `game_id`；业务分支和存档不得继续传播别名。

### 3.2 “专用头已注册”必须是生产者到消费者闭环

不能只检查发送代码里有没有 header。完整注册至少要证明：

1. 生产端在正确模型请求上写入身份；
2. 网关入口实际收到相同值；
3. 需要按游戏分流的每个消费者都有显式分支；
4. 归档不会落入“网关提醒”等通用兜底；
5. 下一轮 `last4` 能看到正确游戏标签；
6. 定向测试覆盖生产、消费、归档和下一轮回读，而不是只断言 wrapper 参数。

header 只有生产者、没有消费者，不叫注册；消费者存在但生产请求没带，也不叫注册。

### 3.3 模型可见文案全部先审

以下内容都算模型可见文案，必须逐字列给辛玥确认后才能写入：

- A 类游戏选择说明与执行说明；
- B 类动态 system 的全部状态分支；
- 独立 user、空 user 与局内消息包装规则；
- 所有精确首行指令、协商、结束和重试文案；
- 会进入主聊天归档、摘要、`last4` 或工具结果摘要的游戏事件文案；
- header 对应的模型可见标签或事件说明。

“只用于内部”“只是归档”“只是重试”都不能免审。确认一版只授权那一版原文，不得施工时顺手补句子。

### 3.4 两种存档不能混为一谈

- **游戏存档**负责权威棋局/资源/回合/局内聊天和结束状态。
- **主聊天归档**负责让渡后续仍知道刚才发生的是哪一个游戏事件。

游戏存档成功不代表主聊天归档正确，主聊天归档成功也不代表动作已经落地。两边必须分别设计、分别验证。

## 4. A 类：渡自主单机游戏

### 4.1 现行标准链路

现行主动单机链路是：

`随机唤醒决策` → `action=game + game_id` → `_PROACTIVE_SOLO_GAMES` 规范化 → `_run_proactive_game_action()` → 指定工具实际调用 → 核对 exact tool trace → 记录 `game:<game_id>->executed/failed`。

不能只让模型说“我玩了”。所选工具未出现在实际执行 trace 中，本轮就必须判定为未成功游玩。

### 4.2 必须登记的入口

1. **游戏能力**
   - 有统一引擎的，登记 `services/game_tool_runtime.py` 中的 ID、别名、保存根、命令和 executor。
   - 外部或独立服务游戏，登记其 bridge、tool schema、executor 和错误合同。

2. **工具能力**
   - 工具名必须唯一，schema 和 executor 必须成对。
   - 模型执行轮必须确实拿到该工具；不能只把工具写进 registry，却没有进入最终请求。
   - 工具返回要能支持下一步决策、终局和错误判断；不得只返回“成功”。

3. **主动单机注册**
   - 在 `services/telegram_proactive.py::_PROACTIVE_SOLO_GAMES` 登记 `title`、`tool` 和经辛玥审过的 `instruction`。
   - 在 `_PROACTIVE_SOLO_GAME_ALIASES` 登记允许别名。
   - 若控制 JSON 允许直接把游戏 ID 写进 `action`，同步登记 direct-action 兼容。
   - 同步登记对外选择列表、执行记录标签和失败原因。
   - B 类共同游戏禁止进入该表。

4. **请求身份和工具循环**
   - 主动执行轮必须保留 `X-DU-WAKEUP-KIND: proactive_game`。
   - 若该游戏需要专用工具模式或游戏工具循环，必须登记对应 header 的生产端和消费者；现有随机塔防使用 `X-Random-Imitator-TD` 触发专用工具模式。
   - 使用通用 `X-DU-Game-Tool-Loop` 时，要验证游戏工具 marker、停止条件、终局和 checkpoint 被统一循环识别。
   - 禁止新增一个无人读取的“游戏专用 header”来假装完成注册。

5. **执行与记录**
   - 执行前先读当前状态，再至少完成一步真实推进；具体顺序由已审 `instruction` 决定。
   - 返回后核对所选 exact tool 是否真实执行。
   - 成功和失败都写入主动决策记录，至少包含 `game_id`、executed/failed 和直接原因。
   - 若游戏工具结果会进入摘要缓存，必须验证本游戏 marker 和清洗，不得退化成整段原始面板。

### 4.3 A 类 App 参与面

App 页面可能只是观察器或人工入口，不能据此改变 A 类模型链定义。仍需登记：

- 游戏大厅卡片和可用状态；
- status/session API；
- 页面加载、空态、错误和刷新；
- 若 App 允许玩家直接改变同一份状态，必须说明这是单机状态的人工操作，还是另外新增了一条 B 类互动链。

仅轮询状态不得制造“辛玥刚和渡互动”的活动记录。

### 4.4 A 类最低回归

- 选择列表出现新游戏且共同游戏不出现；
- 正式 ID、每个批准别名和 direct action 都归一到同一 ID；
- 无效 ID 明确失败；
- 执行轮最终请求包含所选工具及所需模式 header；
- 模型只说文字、不调用 exact tool 时判失败；
- 调用其它游戏工具时判失败；
- 成功/失败执行记录包含正确 `game_id`；
- checkpoint、终局、工具摘要与存档按该游戏合同运行；
- App status/页面只读轮询不刷新共同游戏互动时间。

## 5. B 类：小玥与渡真实互动游戏

### 5.1 现行标准链路

共同游戏的完整链路是：

`App 真实操作` → `权威状态机接受事件` → `登记共同游戏互动时间` → `构造当前游戏 system 与独立 user` → `游戏专用 wakeup wrapper` → `SumiTalk 统一 Prompt 组装` → `渡回复` → `精确解析` → `动作落地` → `局内存档/界面更新` → `专用主聊天归档` → `下一轮 summary/last4 继续识别该游戏`。

任何一段缺失都会形成半接入。

### 5.2 引擎、路由和客户端

1. 在统一游戏运行时登记稳定 ID、别名、保存根、命令和 executor。
2. 提供纯状态/动作 API；读取与写入语义分开，状态读取不得顺带触发模型或互动时间。
3. 需要渡参与时，使用本游戏独立 `/sync-du`，不要让通用动作 API偷偷调用模型。
4. 客户端必须补齐：
   - `GameToolsGatewayClient` 的 DTO、status、command 和 sync；
   - `GameHallScreen` 的 destination、卡片、状态预取和页面跳转；
   - 游戏页面的权威快照、轮次/待处理状态、输入、动作锁、失败重试、结束/重开；
   - 局内消息若要求持久化，必须由服务端快照恢复，不能只放 Compose 临时状态。

### 5.3 动态 system 与独立 user

共同游戏必须通过 `_send_wakeup_event(..., sumitalk_prompt_assembly=True)` 复用 SumiTalk 完整组装面。

- 当前棋盘、轮次、pending、协商和本轮事件属于临时动态 system；发送时显式携带 `__dynamic__=True` 与 `__temporary_dynamic__=True`。
- 位置固定为常驻动态之后、Thinking/`last4` 之前，不得进入 static cache prefix。
- 小玥当前说的话按已审合同放独立 `user`；没有正文时使用已审空 user 原文。
- 必须保留统一近期摘要和 `last4`。不得因怀疑上下文干扰就删除它们，也不得用局内 `game_chat_messages` 替换主聊天上下文。
- 局内聊天历史是否进入当前状态 system，必须由该游戏单独设计并审阅；不能擅自增加、截断或复写。

### 5.4 专用 `wakeup_kind` 和归档身份

每个 B 类游戏必须使用唯一且稳定的 `wakeup_kind`，默认与 `game_id` 相同。

完整登记点：

1. 本游戏 wrapper 调用 `_send_wakeup_event(wakeup_kind=<game_id>)`；
2. `_send_wakeup_event` 产生 `X-DU-WAKEUP-KIND: <game_id>`；
3. `routes/chat.py::_gateway_event_source_for_archive()` 能从最终请求找到本游戏动态 system；
4. `routes/chat.py::_compact_gateway_event_for_archive()` 有本游戏专属 label 和经审阅的内容；
5. 若 assistant 也需要专属压缩，必须有独立分支，不能误用其它游戏；
6. 归档后的 role/label/content 符合合同；
7. 下一轮 `last4` 显示本游戏名，不得显示“网关提醒”；
8. 回归必须实际走到最终请求组装、归档和下一轮回读。

只完成第 1、2 项不算注册完成。五子棋曾经发送 `wakeup_kind=gomoku`，但归档消费者未登记，最终回落成“网关提醒”；这类漏接必须由上述闭环测试直接拦住。

### 5.5 回复协议与动作落地

- 需要模型行动的游戏，第一行精确指令及可选动作必须逐字审阅。
- 解析器只接受获批协议；不得擅自兼容半角标点、空格、异体符号或正文中间指令。
- 根据当前轮次、pending 请求和身份建立允许动作矩阵，不能只“解析成功”就执行。
- 模型回复、协议解析、引擎动作和 UI 展示必须区分成功层级。
- 模型请求成功不等于动作有效；动作无效不得伪装成已落地。
- 是否保存无效回复、是否允许重试以及重试是否再次调用模型，都必须先形成明确合同；不得临时加重试 Prompt、自动落子或兜底动作。

### 5.6 两种消息与结束语义

1. **局内消息**
   - 明确 speaker、原文、追加时机、加载恢复和新局清理规则。
   - 若要求随新局清空，就在权威 `new_game` 状态初始化中清空；不能只清 UI。
   - 不得新增条数、字符数、轮数或正文截断，除非辛玥先批准具体限制。

2. **主聊天归档**
   - 记录这是哪个游戏、发生了哪类事件以及渡如何回应。
   - 归档文案会进入 summary/`last4`，因此属于模型可见 Prompt 审阅范围。
   - 不能用通用“网关提醒”替代已知游戏身份。

3. **结束/重开**
   - 明确谁能结束、结束状态、终局通知、重开是否新局、哪些局内数据清空、哪些长期数据保留。
   - 终局小纸条、协商结局或最后回应仍属于真实互动和归档链，不能漏掉。

### 5.7 真实互动时间

每个 B 类游戏必须先在 `services/user_activity_context.py::SHARED_GAME_ACTIVITY_NAMES` 登记 `game_id -> 游戏名`，再统一调用 `mark_shared_game_user_activity()`。

施工前必须填写事件矩阵：

| 事件 | 默认要求 |
| --- | --- |
| 成功开局/重开 | 刷新 |
| 小玥有效落子、掷骰、选择、提交或其它状态动作 | 刷新 |
| 小玥发送非空局内消息 | 刷新 |
| 求和/悔棋/任务等请求 | 刷新 |
| 同意、拒绝、验收、打回等决定 | 刷新 |
| 小玥主动发起的 `/sync-du` | 刷新 |
| 渡的有效行动真正落地 | 按同一同步事件记录，不得遗漏或重复造时间 |
| 结局确认、终局小纸条等真实回执 | 刷新 |
| status、页面预取、后台轮询、预览 | 不刷新 |
| 只选中格子但未提交 | 不刷新 |
| 非法动作、未被状态机接受的请求 | 不刷新 |

具体游戏可以有不同事件，但必须逐项说明。刷新点放在事件已被权威入口接受的位置；不能只在客户端点击时写，也不能只给 `/sync-du` 一处补时间后声称全覆盖。

互动时间验证必须检查：

- 允许的每个事件分别触发一次正确 `game_id/source/detail`；
- 只读和失败事件不触发；
- 新时间能参与“最近一次聊天或共同游戏互动”的统一比较；
- 测试 mock 外部写入，不得触碰真实 R2。

### 5.8 B 类最低回归

- ID、别名、保存根、路由和客户端 DTO 一致；
- 所有获批 system/user 分支逐字匹配；
- 最终模型请求中当前游戏 system 位于临时动态区，user 独立，summary/`last4` 保留；
- 专用 `X-DU-WAKEUP-KIND` 从 wrapper 到 chat 消费端完整命中；
- 真实归档得到专用游戏 label，不落通用分支；
- 下一轮 `last4` 仍明确显示本游戏身份；
- 首行协议、允许动作矩阵、非法指令和状态机落地均覆盖；
- 局内聊天能重载，并按新局合同清理；
- 每个真实互动事件与每个只读/失败事件都覆盖活动时间断言；
- 原生页面覆盖大厅进入、状态恢复、动作、pending、失败重试、结束/重开；
- 旧 Bug 回归必须在修复前失败，且不能 mock 掉最终 Prompt 组装、归档或下一轮回读边界。

## 6. 禁止用这些证据冒充完成

- wrapper 单测看到 `wakeup_kind` 参数，不等于 header 消费和归档注册完成；
- `/sync-du` 返回 200，不等于模型动作已解析并落地；
- 游戏 JSON 已保存，不等于局内消息、主聊天归档和后续上下文正确；
- 当前 system 已生成，不等于最终上游请求顺序正确；
- `cache_debug` 有动态区，不等于其中一定是当前游戏正文；
- App 能打开页面，不等于渡参与链已接入；
- 本地测试绿，不等于真实模型、设备或生产已验收；
- 给一条路径刷新活动时间，不等于所有真实参与事件都覆盖；
- 新增重试、过滤、截断或上下文替换，不等于修复根因。

## 7. 开工与交付模板

### 7.1 开工前

1. 建立 Task Ticket，明确 A/B 类型及是否双注册。
2. 画出本游戏从入口到下一轮上下文的完整调用链。
3. 填完第 2 节接入清单和 B 类互动时间矩阵。
4. 列出全部新增/修改的模型可见文案原文，等辛玥确认。
5. 写出旧实现会失败的回归路径；不能只测新函数返回值。
6. 检查目标文件是否已有隔壁脏改，命中即停止，不覆盖。

### 7.2 交付时

逐项汇报：

- 实际新增了哪些注册点；
- 每个 header 的生产者和消费者；
- Prompt/system/user/归档文案是否逐字采用获批版；
